# ページごとの判断: `instant = false` を外す

ルートの `instant = false` を外した後もまだブロックしていて、dev overlay の fix card だけでは足りないときに読む。ここの各セクションは、エージェントが単独で下すべきでない判断を扱う。

## ブロッキングな読み取りへの対処を決める

編集の前に、fix card の背後にあるリンク先ページを全文読む。インラインスニペットだけではない。カードはビルドをアンブロックするが、ルートのナビゲーションを実際に instant にする詳細はページ側にある。たとえば `<Suspense>` boundary の置き場所である。即興で直さない。

どの修正が合うか確信がないとき、正しい判断はたいてい、ページのその部分が何のためにあるかに依存する。それはコードには表れない。推測せず、ユーザーにその部分の目的を尋ねる。プロダクト/UX の質問として組み立てる。このコンテンツはロード時に即座に表示されるべきか、少し後からストリーミングされて入るのでよいか。全員が同じものを見るべきでキャッシュ可能か、それともユーザーごと・リクエストごとか。技術的な修正をその答えに結びつける。キャッシュするか、`<Suspense>` でラップするか、リクエスト時のままにするか。こうすればユーザーは API ではなく体験を決めることになる。

## セキュリティゲートなど、推測できないコード

ブロッキングなコードが、推測できない理由でそこにあるように見える場合は、リファクタリングの前に停止してユーザーに尋ねる。たとえばページ先頭のセキュリティゲートである `await verifyAccess()`、認証リダイレクト、フィーチャーフラグのチェックで、`<Suspense>` の中へ移すとコードが保証する内容が変わる場合である。ビルドエラーは `<Suspense>` を求めるが、ゲートを `<Suspense>` でラップするとゲートが無効になる。どうすべきかを知っているのは書いた本人だけである。選択肢は、ルートをブロックしたままにする、つまり文書化された Block としての `instant = false`。ゲートの実行方法が変わるようにページを再構成する。チェックを [Proxy](https://nextjs.org/docs/app/api-reference/file-conventions/proxy) に移す。あるいは、ゲートがアプリの他所で既に依存している保護と重複しているなら削除する。Vercel Deployment Protection のようなプラットフォーム認証、Proxy のチェック、Data Access Layer が該当する。

読み取りの移設、つまり `await connection()` や Proxy への移動は、どこで実行されるかを変えるだけで、そもそも実行されるべきかどうかは変えない。そのため、冗長または壊れたゲートは、fix card のレンズを通すと正しく配置されたゲートと同一に見える。ゲートが奇妙、冗長、場違いに見えるなら、黙って移設するのではなく率直にそう言う。「これはここには不要かもしれません。本当に必要ですか?」と。疑念を表面化させるのがエージェントの仕事であり、決めるのはユーザーである。

レイアウト配下のすべてのルートがこの形でゲートされているなら、レイアウトへの文書化された Block が正しい最終状態である。ゲートを [Proxy](https://nextjs.org/docs/app/api-reference/file-conventions/proxy) に移すのはアーキテクチャの修正であって Cache Components の修正ではなく、移行を止めてまでやることではなくフォローアップである。

より広い視点には、[Authentication guide](https://nextjs.org/docs/app/guides/authentication) と [Data Security の Data Access Layer セクション](https://nextjs.org/docs/app/guides/data-security#data-access-layer) を読む。前者は認証チェックの置き場所を扱う。ルーティングは Proxy、データは Data Access Layer である。後者は `'use cache'` と組み合わせられる集中的な認可チェックを扱う。

あるコードの動作を変えずに Cache Components 的に正しくする方法が分からないなら、尋ねる。

## Block を残す場合

ルートが本当にブロックすべきものである場合、つまり本質的にリクエストごとで有用な静的シェルがない場合、あるいはリファクタが大きく、ユーザーが今は取り組みたくない場合、それは正当な結末である。`instant = false` を残すが、必ず先にユーザーに確認し、その `// TODO: Cache Components adoption` コメントを理由に書き換える。例: `// instant = false: 意図的に維持 — 完全にリクエスト時のダッシュボード` や `// instant = false: 保留 — 現時点ではリファクタが大きすぎる`。

文書化された意図的な Block は移行後に残してよい。文書化されていない置き忘れのオプトアウトは残してはならない。
