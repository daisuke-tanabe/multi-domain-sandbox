# RED テストの堅牢性: 最適化の前に RED を検証する

ワークフローの C-gate。誤った理由で赤い RED は、壊れてなどいなかったルートの最適化へあなたを送り込む。ルートは instant になったのにテストは赤いまま、あるいは壊れたアサーションを満たすためにコードが歪められ、労力は間違った問題に費やされる。予防は安い。まず数分かけて RED が信頼できることを検証する。

## 決着をつける質問

> マーカーはロックなしで、テストユーザーとしてレンダリングされるか。

- No: テストが赤いのは、そのユーザーまたは環境にマーカーやページが存在しないからだ。マーカーのバグであり、instant navigation のバグではない。マーカーを直す。これが最も多いケースである。
- Yes: マーカーは実在し到達可能で、ロック下の赤は本物の「instant ではない」である。ルートを最適化する。

以下のすべては、この質問に正直に答えるためにある。

## ブロックされたルートがビルドできないとき

Cache Components では、top-level のブロッキング読み取りがテストが RED を出す前にビルドを失敗させることがある。一時的な RED 足場の一部として、対象ルートに `export const instant = false` を追加する。既知のブロッカーを、ナビゲーションを instant にすることなくビルド可能にする。修正と同時にオプトアウトを外し、differential のために修正を revert するときはオプトアウトも含めて戻す。

## cookie と session の読み取りはロックの probe ではない

`cookies()` や session の読み取りだけで RED を作り出さない。testing のロックはナビゲーションを shell に制限するのであって、request の cookie を利用不能にするのではない。ルートの実際のブロッキングな uncached データを使い、遅延コンテンツがあるなら self-validating 変種を優先する。

## 堅牢性チェックリスト。すべて成り立つこと

1. baseline で赤い: 未修正のルートで失敗する。
2. 正しい理由: ロックなしなら、production ビルドの rig 上でマーカーが可視である。決して `next dev` ではなく、作者自身のログインセッションではなくテストユーザーとして実行して確認する。
3. differential: 修正だけを revert すると RED、再適用すると GREEN。ほかの何も色を動かさない。
4. ゲーム不能なマーカー: static shell の sync な要素であり、決してストリームされるデータではない。
5. production ビルドで決定的: N 回の実行で安定している。決して `next dev` ではない。
6. 双方向に判別する: instant なルートではロック下で存在し、ブロックするルートではロック下で存在しない。
7. テストユーザーにレンダリングされる: そのユーザーのフラグ・プラン・ロール・データの下で。
8. 条件付きリダイレクトを考慮済み: そのユーザーにとってのルートの実際の到達先でアサートする。
9. 実在するセレクタ: 既知の static-shell ノードに付けた `data-testid` であり、当て推量の `role`/`name` ではない。
10. 可視のマーカー: `display:none` でも画面外でも hover オーバーレイの中でもない。リストでは `.filter({ visible: true }).first()` を対象にする。
11. テスト対象のビルドが新しい: 計測される deployment が最新コミットを含む。前の deploy をまだ配信している build URL ではない。

## 分類: 誤った理由で赤い

以下のいずれも RED を信頼できなくする。どれも「ナビゲーションが instant ではない」ではない。

| 誤った理由 | 起き方 | 排除の仕方 |
| --- | --- | --- |
| セレクタが何にもマッチしない | 当て推量の `getByRole('button', { name: 'Folder' })` | コンポーネントを grep して実際のアクセシブルネームを確認し、`data-testid` を追加する |
| 条件付きリダイレクト | フラグやロールによりテストユーザーに対してルートが `redirect()` し、マーカーのページに到達しない | ページのトップレベルの分岐を確認し、実際の到達先でアサートするか、フラグを固定する |
| フラグ / プラン / ロールのゲート | 作者はフラグやプランを持つが、テストユーザーは持たない | ロックなし baseline をテストユーザーとして実行し、プロジェクトの override 機構でフラグを固定する |
| empty state | マーカーはデータがあるときだけ存在し、CI アカウントは空 | empty state でも存在するマーカーを選ぶ。ページヘッダーのようなレイアウト要素にするか、データを seed する |
| タイムアウト / フレーク | 遅い API や一時的なインフラエラー | 再実行し、インフラのフレークと本物のシグナルを切り分ける |
| ストリームされるマーカー | マーカーが `<Suspense>` の背後にあり、決して shell に入らない | sync な shell 要素を選び、すべての `<Suspense>` の外にあることを確認する |
| 認証リダイレクト | 未認証 → `/login` | ナビゲーションの前にログインが成功していることを確認する |
| stale な deployment | テストが前のビルドに対して走った。テスト対象の URL がまだ前の deploy を配信している | 判定を信頼する前に、最新コミット由来のマーカーを deployment でポーリングする |
| 非表示 / 画面外 | testid が hover オーバーレイや画面外のリストアイテムにある | 常に可視のノードにマーカーを置く。リストでは `.filter({ visible: true }).first()` |

## 実例

実際の最適化実行で起きた失敗の例である。どれも誤った理由で赤く、どれも instant navigation の問題ではなかった。あるアプリのドリフト面は feature flag とプランに支配され、別のアプリでは auth 状態、空のデータベース、locale に支配される。分類はすべての誤った理由を列挙し、rig ファイルの DRIFT リストがどの行が自分のアプリに当てはまるかを示す。

- 当て推量のセレクタ + empty state: マーカーは、どの要素も実際には持っていない当て推量のアクセシブルネームで選んだボタンで、しかも CI アカウントに行が 1 つもないリストページだった。→ チェック 7、9。修正: 実在する static-shell ノードへの `data-testid`。
- 非表示のマーカー: testid は最初 `hidden sm:block` の hover オーバーレイのリンクに、次に画面外のカルーセルカードにあった。Playwright は要素を解決したが hidden と報告した。→ チェック 10。修正: 常に可視のノード。リストでは `.filter({ visible: true }).first()`。

## Differential チェック。PR に残す

RED がその性質を計測していたことの最も強い証拠:

```
1. on the fixed branch → GREEN
2. revert ONLY the fix (the <Suspense> push-down) → RED
3. re-apply → GREEN
4. confirm no other change moves it
```

2 つの実行をリンクするか、切り替えの diff と結果を PR の説明に含める。differential を見たレビュアーは、テストがその性質を計測していると分かる。

## `instant()` はストップウォッチではない

参照: [`instant()`](https://nextjs.org/docs/app/guides/instant-navigation#prevent-regressions-with-e2e-tests)。

このテストはナビゲーションの速さを計測しない。`instant()` は dynamic data をゲートし、static shell の内容をアサートできるようにする。シグナルは存在であり、速度ではない。ロックの下では、instant なルートの shell は存在し、ブロックするルートのコンテンツは待ち時間に関係なく決してコミットされない。したがって:

- 出荷するアサーションはロック下の `await expect(SHELL_MARKER).toBeVisible()` である。カスタムタイムアウトや `painted` の boolean を足さない。
- `3000` のようなカスタムの短いタイムアウトは、存在しない時計との競争を仮定する。判定に何も加えず、コミットがマイクロタスク 1 つ分遅れただけの instant なルートに偽の RED を招く。
- `locator.isVisible({ timeout })` をソフトな待機として使わない。Playwright はそのタイムアウトを非推奨にして無視しており、呼び出しは即座に返る。
- 「テストユーザーにレンダリングされる」、つまりチェック 7-9 は、ロックなし baseline の足場で作成時に確立するものであり、出荷テスト内の時間付きアサーションで確立するものではない。

## `instant()` ガードに retry も prefetch ウォーミングも要らない

`instant()` ガードは決定的である。retry を設定せず、prefetch を間に合わせるための hover ウォーミングもしない。ロックの下では router が route prefetch を開始し、コミット前にそれを待つ。`prefetch={false}` のリンクでも、既に prefetch cache にあるルートでも同じである。したがってコミットされる shell は、事前のレンダリング、hover、メニュー開閉による prefetch に依存しない。フレーキーなガードには実際の原因がある。遷移先 shell の sync ノードでないマーカー、テストユーザーのフラグ・ロール・empty-state のギャップ、あるいは本当にブロックしているルートである。修正はページかマーカーの側にあり、retry はガードが捕まえるべきリグレッションを隠す。正当な `.hover()` やメニュー開閉は、トリガー要素自体が hover や開閉まで DOM に存在しない場合だけである。

## 静かな no-op: 計測対象のビルドで testing API が公開されていること

`instant()` は cookie (`next-instant-navigation-testing`) を設定し、ビルド内のロックコードがそれを読むことで動く。そのロックコードが存在しなくても throw しない。throw するのはネストした呼び出しか不明な base URL のときだけである。testing API なしで生成されたビルド、つまり `experimental.exposeTestingApiInProductionBuild` のないビルドでは、cookie は無視され、ナビゲーションは通常どおり実行され、`instant()` テストは空虚に pass する。緑の `instant()` テストはロックが効いた場合にだけ意味を持つ。

防御は 2 つあり、両方使う:

1. 対象で API が公開されていることを確認する。フラグをプラットフォームの preview/staging 条件か明示的な環境変数に配線する。rig ファイルがプロジェクトの綴りを記録する。SKILL.md のフェーズ 0 と A を参照。フラグが設定されていないビルドからの pass を信頼しない。
2. テストを self-validating にする。遅延コンテンツを持つルートでは、shell の存在だけでなく、遅延コンテンツがロック下でゲートされていることもアサートする。`test-template.md` の self-validating 変種である。ロックが効かなければコンテンツは既に存在し、`toHaveCount(0)` が失敗する。

   ゲート側はウォーム状態に関係なく、両ナビゲーション種別でロックの下で成り立つ。soft-nav のクライアントロックは dynamic-data の書き込みをゲートし、initial load ではサーバーが document リクエストの cookie を尊重して dynamic data をサスペンドする。空虚な pass が可能なのは testing API なしで生成されたビルドだけであり、それは上の防御 #1 がカバーする。

## 決定性と rig

- 常に production ビルドで計測し、決して `next dev` では計測しない。SKILL.md のフェーズ A がこの不変条件とその根拠を持つ。
- RED を複数回実行する。断続的にしか赤くないゲートはゲートではない。フレークするなら、どちらの色も信頼する前に、原因が一時的なエラーのようなインフラなのか本物のレースなのかを見極める。
